System Model #

This section establishes the formal model underlying our garbage collection proofs. We consider a distributed system with the following properties:

Definition (Network Model) #

The system operates under an eventually synchronous network model, characterized by the following guarantees:

  1. Messages may be delayed arbitrarily but are eventually delivered
  2. No message is lost permanently (fair-loss links with retransmission)
  3. Replicas may be partitioned but eventually reconnect
  4. No Byzantine failures (all replicas faithfully execute the protocol)

Definition (Replica Set) #

R = {r₁, r₂, ..., rₙ} is a finite, known set of replicas. Each replica maintains local state sᵢ and a logical clock clockᵢ.

Definition (CRDT State Space) #

A CRDT C = (S, ⊔, eval) where S is the state space, ⊔ : S × S → S is a join-semilattice merge, and eval : S → V extracts the user-visible value.

Definition (Semantic Equivalence) #

Two states s₁ ≡ s₂ are semantically equivalent if and only if eval(s₁) = eval(s₂). States may differ in internal representation—such as tombstone sets or metadata—while remaining equivalent from the user's perspective.

Membership Assumption

These safety proofs assume static membership: the replica set R is fixed throughout system execution. Supporting dynamic membership (replicas joining or leaving) requires additional view-change protocols not addressed in this document.

GC Safety Requirements #

Garbage collection in CRDTs must preserve convergence guarantees while reclaiming space. Formally, a GC scheme is a pair (gc, stable) where gc : S → S is the collection function that removes tombstones, and stable : Tombstone × Replica → Bool is the predicate that determines when a tombstone is safe to collect.

Definition (GC Safety) #

A garbage collection scheme (gc, stable) is SAFE for CRDT C iff it satisfies properties GC-1' through GC-3':

GC-1' (Monotonic Projection)

gc(s) ⊑ s ∧ (s₁ ⊑ s₂ ⟹ gc(s₁) ⊑ gc(s₂))
This property states that GC only removes information—never adds it—where ⊑ denotes the lattice ordering. Additionally, GC preserves the relative ordering between states. This requirement is deliberately weaker than requiring gc to be a join-homomorphism, since the stronger property fails for non-deterministic GC implementations.

Why Not Join-Homomorphism?

The naive formula gc(s₁) ⊔ gc(s₂) = gc(s₁ ⊔ s₂) cannot hold for non-deterministic GC. If gc can choose which stable tombstones to collect, two replicas might make different choices, breaking equality. For this stronger property, GC must be deterministic: given the same stability information, always collect the same tombstones.

Definition (Deterministic GC) #

A GC function gc is DETERMINISTIC iff for all states s₁ ≡ s₂ with identical stability information: gc(s₁) ≡ gc(s₂).

GC-1 (Join-Homomorphism (Strong, requires deterministic GC))

∀ s₁, s₂. stable(t, s₁) ∧ stable(t, s₂) ⟹ gcₜ(s₁) ⊔ gcₜ(s₂) = gcₜ(s₁ ⊔ s₂)
When GC is deterministic and targets a specific tombstone t, the strong homomorphism property holds under stability preconditions. The subscript t denotes GC targeting tombstone t specifically.

GC-2' (Stability Soundness)

stable(t, r) ⟹ ∀ r' ∈ R. t ∈ observed(r')
This property ensures the stability oracle is sound: whenever it reports a tombstone t as stable, all replicas have indeed observed t. This soundness requirement is essential for implementability—in an asynchronous distributed system, no replica can directly verify what other replicas have observed.

Definition (Stability Oracle) #

A stability oracle is a function stable : Tombstone × Replica → Bool that can be implemented by one of the detection methods below. Each method requires specific network assumptions for soundness.

GC-3' (Semantic Preservation)

eval(gc(s)) = eval(s)
GC must preserve the user-visible value: the eval function extracts identical results before and after garbage collection. This formulation provides a cleaner semantic requirement than alternative predicates that reason about operation applicability.

GC-4 (Liveness (Progress))

∀ t. ◇(∀ r ∈ R. stable(t, sᵣ)) ⟹ ◇(∀ r ∈ R. t ∉ sᵣ)
Once a tombstone becomes stable at all replicas, it must eventually be collected at all replicas. This liveness property ensures GC makes progress and prevents unbounded tombstone accumulation.

Stability Detection Methods #

Each stability detection method implements the stability oracle with specific assumptions:

Lemma: S1 (Vector Clock Stability)

Define stable_vc(t, r) := min{VCᵣ[i] : i ∈ R} ≥ t.clock. Under causal delivery (no message reordering), stable_vc satisfies GC-2'.

Proof:

If min(VCᵣ) ≥ t.clock, then for all replicas r', VCᵣ[r'] ≥ t.clock. By vector clock semantics under causal delivery, this means r has received confirmation (via transitive message chains) that r' has logical time ≥ t.clock. Since t was created at t.clock, r' must have observed t. ✓

∎

Lemma: S2 (Acknowledgment Stability)

Define stable_ack(t, r) := ∀ r' ∈ R. ack(r', t) ∈ received(r). Under reliable delivery with retransmission, stable_ack satisfies GC-2'.

Proof:

Each replica r' sends ack(r', t) only after observing t. Under reliable delivery, if r has received ack(r', t), then r' did observe t. If acks can be lost, retransmission ensures eventual delivery; the oracle waits until all acks arrive. ✓

∎

Ack Loss

If an ack is lost and not retransmitted, stable_ack may never return true (liveness failure) but remains sound (no false positives).

Lemma: S3 (Checkpoint Stability)

Define stable_cp(t, r) := t.clock < checkpoint_epoch(r). Under synchronous checkpoint protocol (all replicas confirm reaching checkpoint before any proceeds), stable_cp satisfies GC-2'.

Proof:

The checkpoint protocol guarantees: no replica advances past checkpoint C until all replicas reach C. Reaching C requires having received all operations with clock < C, including t. Therefore, if r has checkpoint_epoch > t.clock, all replicas observed t. ✓

∎

Checkpoint Implementation

Checkpoints guarantee causal consistency (all ops before C are delivered), not necessarily state equality. Replicas may have different representations but are semantically equivalent (s₁ ≡ s₂).

Lemma: S4 (Time-Based Stability)

Define stable_time(t, r) := now(r) > t.timestamp + D. Given bounded clock skew ε and maximum message delay δ, if D > ε + δ, then stable_time satisfies GC-2'.

Proof:

Let t be created at physical time T (by creator's clock). Any replica r' has clock within ε of true time. Message carrying t arrives within δ of send time. If now(r) > T + D and D > ε + δ, then sufficient real time has passed for t to reach all replicas. ✓

∎

Time-Based Assumptions

This method requires known bounds on clock skew (ε) and message delay (δ). In truly asynchronous networks where δ is unbounded, time-based stability is unsound.

Epoch and Version Vectors #

To track GC progress across replicas, we introduce epoch vectors:

Definition (GC Epoch) #

A GC epoch e is a monotonically increasing identifier representing a GC generation. Each replica maintains epochᵣ indicating the highest GC epoch it has applied.

Definition (Epoch Vector) #

An epoch vector EV = [e₁, e₂, ..., eₙ] where eᵢ is replica rᵢ's last known GC epoch as observed by the local replica.

EV-1 (Epoch Vector Update)

On receiving message m from replica rⱼ with epoch eⱼ: EVᵢ[j] := max(EVᵢ[j], eⱼ)

EV-2 (Safe GC Epoch Advancement)

Replica r may advance to epoch e+1 iff: min(EVᵣ) ≥ e
A replica only advances its GC epoch when it knows all other replicas have reached the current epoch.

Anti-Entropy Protocol Requirements #

For GC to be safe, the anti-entropy (synchronization) protocol must satisfy:

AE-1 (Tombstone Propagation)

Tombstones must be propagated before they can be collected. The protocol must ensure that if replica A has collected tombstone t, then for any replica B syncing with A, B has already observed t.

AE-2 (Epoch Consistency)

Messages must include the sender's GC epoch. A replica at epoch e must not accept operations from epoch e' > e without first synchronizing the GC state.

AE-3 (Causal Delivery)

send(m₁) → send(m₂) ⟹ deliver(m₁) → deliver(m₂)
Causal delivery ensures that an operation creating a tombstone is delivered before any operation that depends on observing that tombstone.

The Composition Problem #

A critical question: if replicas run GC at different times, do results still converge?

Definition (Asynchronous GC Scenario) #

Replica A with state sₐ runs gc → gc(sₐ). Replica B with state s_B doesn't run GC yet. They sync: gc(sₐ) ⊔ s_B = ?

Theorem: C1 (Asynchronous GC Composition)

For deterministic GC with stability oracle satisfying GC-2', if stable(t, A) holds when A runs gc, then: gc(sₐ) ⊔ s_B ≡ gc(sₐ ⊔ s_B)

Proof:

By GC-2' soundness, stable(t, A) implies B has observed t.

∎

Case analysis on s_B relative to t:
  1. If t ∈ s_B: Both sides contain t's effect. Merging gc(sₐ) (without t) with s_B (with t) preserves the deletion semantics. Then gc on the result removes t.
  2. If B already ran gc and t ∉ s_B: Both gc(sₐ) and s_B lack t. Merge is straightforward; gc is idempotent.
  3. Semantic equivalence (≡) follows from GC-3': eval is preserved through gc. ✓

Synchronous GC Alternative

If asynchronous composition is too complex, the protocol can enforce synchronous GC: checkpoints force all replicas to run GC simultaneously, avoiding the composition problem entirely.

GC Correctness Proofs #

Theorem: 24.1 (Checkpoint GC Safety)

Given:

- Synchronous checkpoint protocol (all replicas confirm reaching C before proceeding)

- Tombstone t created before checkpoint C

- Deterministic gc removes t after checkpoint

- CRDT has add-wins or remove-wins conflict resolution (conflict semantics specified)

Then: gc satisfies GC-1', GC-2', GC-3'

Proof:

We prove each property under the stated assumptions.

∎

GC-1' (Monotonic Projection):
gc(s) ⊑ s: By construction, gc only removes tombstones, never adds information. Removing elements from a join-semilattice produces a smaller element.
s₁ ⊑ s₂ ⟹ gc(s₁) ⊑ gc(s₂): If s₁ ⊑ s₂, then s₂ contains all information in s₁ plus possibly more. Deterministic gc removes the same tombstones (those stable at both states). Since gc preserves relative ordering, gc(s₁) ⊑ gc(s₂). ✓
GC-2' (Stability Soundness):
By Lemma S3 (Checkpoint Stability), stable_cp satisfies GC-2' under synchronous checkpoint protocol. The checkpoint barrier ensures all replicas observed t before any can collect it. ✓
GC-3' (Semantic Preservation):
We must show eval(gc(s)) = eval(s). Tombstones encode deletions; removing a tombstone doesn't resurrect the element because:
  • For remove-wins: The element remains deleted; tombstone was bookkeeping only.
  • For add-wins (e.g., ORSet): Tombstone t only masks adds with IDs concurrent with or before t. By stability, no such adds remain undelivered. Future adds use fresh IDs not masked by t.
In both cases, eval returns the same value before and after gc. ✓

Theorem: 24.2 (Late-Arriving Operation Safety)

If replica A has collected tombstone t (at epoch e_A), and later receives operation op from replica B (at epoch e_B < e_A) where op was concurrent with t's creation, then:

(a) If op does not reference the tombstoned element: applied normally

(b) If op references the element: epoch mismatch triggers resynchronization

Proof:

By AE-2 (Epoch Consistency), messages include sender's GC epoch.

∎

When A receives op from B with e_B < e_A:
  1. A detects epoch mismatch: e_B < e_A
  2. By EV-2, A only advanced to e_A after knowing all replicas (including B) reached e_A - 1
  3. B sending from e_B < e_A means B was partitioned during epoch advancement
  4. A initiates resync: B must catch up to e_A before its operations integrate
  5. After resync, B has observed all tombstones collected up to e_A, preventing conflicts ✓

Partition During Epoch Advancement

This theorem requires that epoch advancement waits for all replicas (EV-2). The epoch vector mechanism prevents premature advancement by blocking until all replicas are observed at the current epoch.

Theorem: 24.3 (GC Liveness)

Under the eventually synchronous network model, if tombstone t is created at time τ, then t is eventually collected at all replicas.

Proof:

By the network model (eventually synchronous):

∎

  1. Tombstone t is created at replica r at time τ
  2. By message delivery guarantee, t eventually reaches all replicas
  3. By epoch vector protocol, eventually all replicas report having observed t
  4. Once min(EV) indicates all replicas have observed t, t becomes stable
  5. By GC-4, stable tombstones are eventually collected ✓
