A valid Stratum specification must satisfy seven semantic invariants. These invariants ensure that every specification is not only syntactically well-formed but also semantically coherent, traceable, and verifiable. Together, they form the foundation for trustworthy system documentation that can be automatically validated and maintained over time.
Each invariant addresses a distinct aspect of specification quality: G1 (Provenance) ensures traceability to purpose; G2 (Fulfillment) ensures completeness; G3 (Non-Contradiction) ensures consistency; G4 (Materialization) ensures groundedness; G5 (Predictability) enables impact analysis; G6 (Stratification) enforces abstraction boundaries; and G7 (Diagnosability) provides actionable error reporting.

Research Foundation

These seven invariants have deep roots in 40+ years of academic literature, industry standards, and formal methods. Each property maps to established concepts from IEEE/ISO standards, SEI publications, OMG specifications, and foundational computer science research.

Provenance #

The Provenance guarantee (G1) corresponds to bidirectional traceability in requirements engineering literature. IEEE 24765 defines traceability as "the degree to which each element in a software development product establishes its reason for existing." ISO/IEC/IEEE 29148:2018 requires that traceable requirements be "upwards traceable to specific documented stakeholder statement(s) of need... and downwards traceable to the specific requirements in the lower tier requirements specification."
The Provenance guarantee ensures that every element in a specification can trace its existence back to a root purpose. Nothing exists without justification—every requirement, design decision, and implementation detail must be connected to the fundamental goals of the system. This prevents orphaned elements that serve no purpose and ensures complete traceability from implementation to intent.
Safety-critical standards enforce this rigorously. DO-178C requires that "every line of code must be traceable to a requirement" (Table A-7, Objective 9). IEC 61508-3 Annex A.1 specifies that backward traceability checks "that the implementation is justified by a requirement"—the core provenance property. In formal methods, the refinement calculus (Back & von Wright 1998) provides mathematical foundations where each refinement step is proven to preserve specification truth.

Definition (Root Element) #

root(e) ≡ layer(e).stratum = purpose ∧ ¬∃d ∈ D. d.tgt.elem = e.id ∧ d.δ = justified_by

Definition (Trace Path) #

tracePath(e) = shortest path from e to some e' where root(e') following justified_by dependencies from target to source (impl → requirement)

GUARANTEE G1 - PROVENANCE

∀ e ∈ E. ∃ e' ∈ E. root(e') ∧ reachable(e, e', justified_by)
Every element in the specification must be reachable from a root element in the purpose stratum via justified_by dependencies, which flow from implementation toward requirement.
Formally, for specification S: Provenanced(S) ≡ ∀ e ∈ elements(S). tracePath(e) ≠ ∅

Fulfillment #

The Fulfillment guarantee (G2) corresponds to constraint satisfaction and model satisfaction (M ⊨ S) in formal logic. Contract-based design (Benveniste et al. 2018) formalizes this through assume-guarantee contracts where a component satisfies a contract if "all runs that satisfy assumptions A must satisfy guarantees G." The compositional theorem states that if all components satisfy their own contracts, a global system contract is satisfied.
The Fulfillment guarantee ensures that a specification satisfies its own declared constraints. Every specification may declare constraints—rules that must hold for the specification to be considered complete. Fulfillment requires that all error-level constraints evaluate to true. This makes the specification self-validating: it defines its own completeness criteria and then meets them.
IEEE 29148:2018 defines "complete" for individual requirements as "needs no further amplification because it is measurable and sufficiently describes the capability." DO-178C specifies 71 verification objectives organized by Design Assurance Level, with completeness requiring evidence that "each phase is complete, coherent, and traceable to its predecessor." The OMG OCL 2.4 Specification requires that "an OCL expression is an invariant of the type and must be true for all instances of that type at any time."

Definition (Constraint Satisfaction) #

S ⊨ c ≡ c.φ(elements(S), dependencies(S)) = ⊤

Definition (Error Constraints) #

ErrorConstraints(S) = {c ∈ constraints(S) | c.sev = error}

GUARANTEE G2 - FULFILLMENT

∀ c ∈ ErrorConstraints(S). S ⊨ c
Every error-level constraint declared in the specification must evaluate to true. This ensures completeness relative to the specification's own stated requirements.
Complexity: evaluating all error constraints is O(|C_error| * T_eval), where T_eval is the cost of a single constraint evaluation over E and D. For finite, quantifier-bounded constraints, this is typically polynomial in |E| + |D|.
Formally: Fulfilled(S) ≡ ∀ c ∈ ErrorConstraints(S). c.φ(E, D) = ⊤
Common fulfillment constraints:
  • ∀ feature f. ∃ test t. tests(t, f) - Feature test coverage
  • ∀ api a. ∃ doc d. documents(d, a) - API documentation
  • ∀ aggregate ag. ∃ command c. commands(ag, c) - Aggregate has commands

Non-Contradiction #

The Non-Contradiction guarantee (G3) maps to internal consistency and satisfiability in formal methods. The classical Law of Non-Contradiction (Aristotle) states ¬(P ∧ ¬P). In SAT/SMT solving, this becomes satisfiability: a set of constraints is consistent iff their conjunction is satisfiable. VDM explicitly defines proof obligations for internal consistency: "A proof obligation is a theorem stating that a certain property must hold in order for a formal specification to be internally consistent."
The Non-Contradiction guarantee prevents semantic conflicts within a specification. When two elements make claims about the same property—such as an API's return type appearing in both the interface definition and its handler implementation—those claims must agree. Contradiction detection identifies cases where elements that should unify actually assert incompatible values, catching integration errors before they manifest as runtime bugs.
For TLA+ specifications, Lamport defines invariants as "state predicates true of all reachable states," with the TLC model checker performing breadth-first search to verify invariance. In Alloy, consistency analysis uses SAT-based model finding: a specification is consistent if at least one valid instance exists that satisfies all facts within a bounded scope. IEEE 29148:2018 requires that requirements be "consistent: free of conflicts with other requirements." The KAOS methodology formally defines conflicts as goals that are "mutually inconsistent under domain axioms."

Definition (Contradiction) #

contradiction(e₁, e₂) ≡ ∃ property p. e₁.π(p) is defined ∧ e₂.π(p) is defined ∧ e₁.π(p) ≠ e₂.π(p) ∧ unifies(e₁, e₂, p)

Definition (Unifies) #

unifies(e₁, e₂, p) ≡ ∃ c ∈ C. c.cat = non_contradiction ∧ c specifies e₁.p must equal e₂.p

GUARANTEE G3 - NON-CONTRADICTION

∀ e₁, e₂ ∈ E. ¬contradiction(e₁, e₂)
No pair of elements may assert incompatible values for any property that a unification constraint requires to match. This prevents semantic conflicts within the specification.
Complexity: a direct check over all constrained pairs is O(|E|^2 k), where k is the average number of properties compared. With indexed constraints and candidate pairing, this can be reduced to O(|D| + |E| k) in typical implementations.
Formally: NonContradictory(S) ≡ ∀ e₁, e₂ ∈ elements(S). ¬contradiction(e₁, e₂)
Common non-contradiction constraints:
  • API return type = Handler return type
  • Event schema = Event handler expected schema
  • Database field type = Domain entity field type

Materialization #

The Materialization guarantee (G4) builds on refinement and reification theory with a 40-year history. C.B. Jones's VDM work defines reification as "finding a more concrete representation of abstract data types"—stepwise transformation with proof obligations via retrieve functions. The He-Hoare-Sanders formulation (1986) introduces downward and upward simulation with abstraction relations ρ ⊆ Σ_A × Σ_C between abstract and concrete states.
The Materialization guarantee ensures that abstract specifications are grounded in concrete reality. Every element at the physical stratum—the lowest level of abstraction—must have a binding that connects it to an actual artifact: a file, a database table, a hardware component. This prevents specifications from describing phantom systems that exist only on paper, ensuring that what is specified actually exists.
Enterprise architecture uses the realization relationship (ArchiMate 3.2): "A dependency relationship that connects a logical entity with a more concrete entity that implements it." The progression flows from Architecture Building Blocks (ABBs) to Solution Building Blocks (SBBs). In MDA, the transformation chain CIM → PIM → PSM → Code represents progressive materialization. A specification is "fully grounded" when the Platform Specific Model produces deployable Executable Object Code.

Definition (Terminal Element) #

terminal(e) ≡ layer(e).stratum = physical

Definition (Materialized Element) #

materialized(e) ≡ ∃ b ∈ B. b.abstract.elem = e.id

GUARANTEE G4 - MATERIALIZATION

∀ e ∈ E. terminal(e) → materialized(e)
Every element at the physical stratum must have an associated binding that maps it to a concrete artifact. This ensures specifications describe things that actually exist.
Formally: Materialized(S) ≡ ∀ e ∈ elements(S). terminal(e) → materialized(e)
Complexity: checking bindings for terminal elements is O(|E_terminal| × |B|) with naive lookup, or O(|E_terminal|) with indexed bindings where each terminal element has O(1) binding lookup.
Materialization types per domain:
  • Software: Component → File:Line
  • Manufacturing: Part → Drawing + BOM
  • Healthcare: Protocol → EMR Configuration
  • Legal: Clause → Document Section

Predictability #

The Predictability guarantee (G5) connects to modifiability and change impact analysis research. The SEI defines modifiability as "a quality attribute that relates to the cost of change and refers to the ease with which a software system can accommodate changes." Bohner & Arnold's foundational 1996 work defines change impact analysis as "identifying the potential consequences of a change, or estimating what needs to be modified to accomplish a change."
The Predictability guarantee enables reliable change impact analysis. Before any change is applied to a specification, the complete set of affected elements can be computed in linear time. This allows teams to understand the full consequences of a proposed change—which tests need to run, which documents need updating, which stakeholders need notification—before committing to it.
Reps, Horwitz, and Sagiv's POPL 1995 paper on IFDS problems provides "a polynomial-time algorithm for finding precise solutions to a general class of interprocedural dataflow-analysis problems." The incremental model transformation literature (VIATRA framework) establishes that "synchronization time is proportional to the magnitude of change and not to the size of models"—precisely the property Predictable(S) requires. Yau & Collofello's ripple effect analysis (IEEE TSE 1985) measures structural stability upon modification.

Definition (Change) #

δ ::= ⟨element: ID, changeType: CHANGE, details: VALUE⟩

Definition (Impact) #

impact(S, δ) = ⋃ {cascade(S, elem(δ), δ.changeType, r) | r ∈ R, r.trigger matches δ}

GUARANTEE G5 - PREDICTABILITY

∀ δ : CHANGE. impact(S, δ) is computable before applying δ
For any proposed change δ, the complete set of affected elements and their effects can be computed in O(|E| + |D|) time before the change is applied. This enables reliable impact analysis and risk assessment.
Formally: Predictable(S) ≡ impact : S × CHANGE → P(E × EFFECT) is total and computable in O(|E| + |D|) time
This enables:
  • Pre-change impact analysis
  • Automated change review
  • Risk assessment
  • Staged rollout decisions

Stratification #

The Stratification guarantee (G6) embodies layered abstraction and Robert C. Martin's Dependency Rule: "Source code dependencies can only point inwards. Nothing in an inner circle can know anything at all about something in an outer circle." A crucial distinction from Abelson & Sussman's work (1987): "Where layers are levels of equal abstraction in software, strata are levels of different abstraction." Layers provide horizontal separation by functional concern; strata provide vertical separation by abstraction level.
The Stratification guarantee enforces clean abstraction boundaries. Dependencies must flow downward through the strata (from purpose through logical to physical), preventing implementation details from leaking into high-level requirements. The sole exception is the justified_by relation, which explicitly links implementations back to the requirements they satisfy—flowing upward to establish provenance.
ArchiMate's three core layers (Business, Application, Technology) formalize this with "higher layers making use of services provided by lower layers" and realization relationships connecting elements across layers. OMG's MOF four-layer metamodel architecture (M0-M3) provides rigorous formalization: "Models at every level conform to a model belonging to the upper level." MOF is closed—M3 conforms to itself. MDA's CIM/PIM/PSM separation achieves vertical separation of concerns with transformations flowing downward.

Definition (Stratum Respecting) #

stratumRespecting(d) ≡ let l_s = layer(src(d)), l_t = layer(tgt(d)) in

rank(l_s) ≥ rank(l_t) ∨ d.δ = justified_by

GUARANTEE G6 - STRATIFICATION

∀ d ∈ D. stratumRespecting(d)
Dependencies must respect stratum boundaries: elements may only depend on elements at equal or lower rank. The justified_by relation is the sole exception, explicitly linking implementations to their requirements.
Formally: Stratified(S) ≡ ∀ d ∈ dependencies(S). stratumRespecting(d)
Complexity: a single pass over all dependencies, O(|D|). Each dependency check requires O(1) stratum rank lookup for source and target elements, making the total verification linear in the number of dependencies.
This ensures:
  • Abstraction boundaries are respected
  • Implementation details don't leak upward
  • Changes cascade predictably (down, not up)
Exception: justified_by dependencies go UP (from impl to requirement)

Diagnosability #

The Diagnosability guarantee (G7) leverages MUS extraction and model-based diagnosis from SAT/SMT theory. A Minimal Unsatisfiable Subset (MUS) is a subset M of an unsatisfiable formula F where M is unsatisfiable but removing any clause makes it satisfiable. Reiter's seminal 1987 paper establishes that "the set of diagnoses is exactly the set of minimal hitting sets of the collection of all conflicts." Junker's QuickXplain algorithm (2004) efficiently computes preferred minimal conflicts using divide-and-conquer with O(n·log(k+1)+k²) consistency checks.
When validation fails, humans need actionable explanations. G7 requires that every violation report includes an irreducible unsat core—the minimal set of constraints causing the failure—and human-readable diagnostic text.
Diagnosability from discrete-event systems theory (Sampath et al. 1995) defines when faults can be unambiguously detected: fault f is diagnosable iff no two infinite runs exist with identical observable projections where f occurs in one but not the other. The hitting set duality—every MUS hits every MCS (Minimal Correction Subset)—enables computing repairs from conflicts. Delta debugging (Zeller 1999) provides 1-minimality for failure-inducing inputs.

Valid Specification #

The seven invariants combine to form the definition of a valid specification. A specification that satisfies all invariants is one that can be trusted: it is traceable to purpose, internally consistent, grounded in reality, and when it fails validation, it explains why. This is the central quality criterion for any Stratum document.

Definition (Valid Specification) #

Valid(S) ≡ WellFormed(S) ∧ Provenanced(S) ∧ Fulfilled(S) ∧ NonContradictory(S) ∧ Materialized(S) ∧ Predictable(S) ∧ Stratified(S) ∧ Diagnosable(S)

A specification is valid iff it is well-formed and satisfies all seven invariants. Note: G7 (Diagnosability) is K1 conformance; K0 implementations check G1-G6 only.

IEEE/ISO standards, OMG specifications (MOF, OCL, MDA), and safety-critical standards (DO-178C, ISO 26262, IEC 61508) independently arrived at nearly identical property definitions, suggesting these validity properties are fundamental to rigorous specification. Every Stratum property maps to concepts with 30-40 years of formal methods research.
