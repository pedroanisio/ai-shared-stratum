2.4 THE STRATUM KERNEL (K0)#

Purpose: The STRATUM Kernel is the irreducible core of the specification—the minimum set of definitions required for K0 conformance. This section provides a self-contained reading guide for implementers who need only the essential framework without certification, concurrency, or advanced features.

Conformance Level K0 (Kernel-Conformant): Implementers reading ONLY the Kernel sections can achieve basic STRATUM conformance. Higher conformance levels (K1: Certified-Aware, K2: Regulated-Pipeline, K3: Live-Graph) require additional sections per §0.4.

Kernel Components

The Kernel consists of six essential subsystems:

1. Data Structures (§3.1 Element – §3.2 Layer – §3.3 Dependency)

Element, Layer, Dependency — the core abstract syntax tree. Read: Definition 2.1 (Element), Definition 2.6 (Layer), Definition 2.11 (Dependency), Definition 2.8 (DEPTYPE enumeration).

2. Constraints (§3.4 Constraint)

QF_LIA + QF_LRA + QF_UF constraint language. Read: Definition 2.12 (Predicate Language), Definition 2.16 (Constraint), Theorem 2.1 (Decidability). Note: SMT-LIB 2.6 standard required for conformance.

3. Well-Formedness (§5)

Structural invariants that all specifications must satisfy. Read: All WF-rules including WF-ID, WF-LAYER, WF-ACYCLIC-HARD, WF-SOFT-CYCLE-BOUNDED, WF-CASCADE-TERMINATION (added v2.4.4).

4. Six Guarantees (§6.1 Traceability – §6.2 Completeness – §6.3 Consistency – §6.4 Groundedness – §6.5 Determinism – §6.6 Coherence)

G1 (Traceability), G2 (Completeness), G3 (Consistency), G4 (Groundedness), G5 (Determinism), G6 (Coherence). These are the semantic properties that define a Valid specification. G7 (Explainability) is K1, not K0.

5. Inference Rules (§8)

Cascade computation (CASCADE-1, CASCADE-N, CASCADE-ATT), constraint satisfaction (CONSTR-SAT), trace computation (TRACE-ROOT, TRACE-STEP). These define the operational semantics.

6. Core Operations (§9.1 Query Operations – §9.2 Modification Operations – §9.3 Comparison Operations)

validate(S) → violations, trace(e) → path, impact(S, δ) → affected elements. These are the three required Kernel operations. Note: validateIncremental (§9.1 Query Operations.1) is K3, not K0.

Kernel Properties

All Kernel operations share three essential properties:

Pure

All Kernel functions are deterministic total functions with no side effects. No I/O, no randomness, no wall-clock time dependencies. Given the same input, always produce the same output.

Decidable

All Kernel judgments terminate with definite yes/no answers. No "unknown" or "timeout" results. Well-formedness checking is O(|E| + |D| + |L|²). Constraint validation is decidable via SMT solving (NP-complete, but terminates).

Compositional

Kernel(S₁ ⊕ S₂) = Kernel(S₁) ⊕ Kernel(S₂). Merging two specifications preserves all Kernel properties. This follows from the CRDT-based merge semantics (§1) but does not require understanding CRDTs for K0 conformance.

What is NOT in the Kernel

The following features are EXTENSIONS, not Kernel requirements:

  • Concurrency (§1 – §14): CRDTs, vector clocks, conflict resolution. Optional for single-user tools.

  • Certification (§15 – §16 – §17 – §18, §23 – §24 – §25 – §26 – §27 – §28 – §29): RTM, DO-178C/ISO 26262 mappings, STPA/FMEA. Only required for K2+ conformance.

  • Advanced Operations (§7.4, §10 – §11): Artifact adapters, domain profiles, extension mechanisms. Useful but not essential.

  • Mechanized Proofs (§17, §19 – §20 – §21 – §22): TLA+, Coq, Lean templates. Helpful for verification but not required for implementation.

  • G7 Explainability (§6.8 Valid Specification): Unsat core generation. This is K1 (Certified-Aware), not K0.

Dependency Direction vs Impact Flow Semantics

Dependencies have TWO distinct directional semantics:

1. Structural Direction (src → tgt): The dependency arrow shows WHO depends ON WHOM.
- d.src → d.tgt means "src depends on tgt" (src is dependent, tgt is dependee)
- realizes: concrete_impl → abstract_spec (impl depends on spec)
- requires: component_A → component_B (A depends on B)
- Coherence (G6): pos(d.src) ≥ pos(d.tgt) (dependent ≥ dependee in concreteness)

2. Impact Flow: CASCADE walks deps where d.src.elem = changed_element, propagates to d.tgt.
- When element e changes, impact flows TO elements e depends on
- Example: Component C realizes Spec S → dependency C → S
- If C changes: cascade finds d.src=C, propagates impact to S ✓
- If S changes: cascade finds deps d.src=S (none of type realizes), no auto-propagation to C
- This prevents circular cascades while maintaining traceability

Reconciling 'changes cascade down': This phrase in §6.6 Coherence means Coherence prevents upward structural dependencies (abstract layers don't depend on concrete). Impact flows along dependency arrows (dependent → dependee), which by G6 is always same-tier or concrete→abstract.

Notation: src(d) = d.src, tgt(d) = d.tgt; d : e₁ →[δ] e₂ means dependency d from e₁ to e₂ of type δ

3.4 Constraint#

A Constraint is a rule that must hold across elements.

SOUNDNESS FIX [v2.0]: The predicate language φ is now formally specified as a combination of QF_LIA, QF_LRA, and QF_UF (Quantifier-Free Linear Integer Arithmetic, Linear Real Arithmetic, and Uninterpreted Functions with Equality). This ensures decidability per SMT-LIB 2.6 standard using Nelson-Oppen combination.

Definition 2.12 (Predicate Language - SMT-LIB Constraint Logic)

The constraint predicate language combines three decidable SMT-LIB theories:

  • QF_LIA: Quantifier-Free Linear Integer Arithmetic (sort Int)

  • QF_LRA: Quantifier-Free Linear Real Arithmetic (sort Real)

  • QF_UF: Quantifier-Free Uninterpreted Functions with Equality

Sorts and Coercions:

Sorts: Int, Real, Bool, Element, Layer, Dependency
Coercion: to_real : Int → Real (standard SMT-LIB coercion)
No implicit coercion from Real to Int (explicit floor/ceil required)

Nelson-Oppen Requirements: QF_LIA, QF_LRA, and QF_UF are stably infinite and have disjoint signatures (Int/Real arithmetic operators vs uninterpreted functions), satisfying combination requirements (Nelson & Oppen 1979).

Terms:

t ::= x : σ                    -- Typed variable (σ ∈ {Int, Real, Bool, Element, ...})
    | n : Int                  -- Integer literal
    | r : Real                 -- Real literal
    | t₁ + t₂ | t₁ - t₂        -- Addition, subtraction (same sort)
    | n × t                    -- Scalar multiplication (n : Int)
    | to_real(t)               -- Int → Real coercion
    | f(t₁, ..., tₙ)           -- Uninterpreted function (signature declared)
    | e.π(p) : VALUE           -- Property access (runtime value)
    | |S| : Int                -- Set cardinality (finite sets only)
    | count(S, pred) : Int     -- Counting with predicate (see below)

Finite Set Cardinality Semantics: The count(S, pred) operator is defined for FINITE element sets only. Given a finite set S ⊆ E and predicate pred : E → Bool, count(S, pred) = |{e ∈ S | pred(e)}|. This is decidable because all specifications have finite E, L, D, C sets per §5 (WF-ID ensures finite identifiers).

SMT Solver Requirements: Constraints using |S| or count() require an SMT solver with BOTH QF_LIA/QF_LRA theory AND finite sets theory (e.g., Z3 with (set Int) or CVC5 with finite sets). Pure QF_LIA + QF_UF solvers cannot handle set cardinality. Implementations may choose to: (1) require sets-capable solver for full K0 conformance, OR (2) restrict Kernel to QF_LIA/LRA/UF only and treat |S|/count() as K1+ extensions.

Atomic Formulas:

a ::= t₁ = t₂                  -- Equality
    | t₁ ≠ t₂                  -- Disequality
    | t₁ < t₂ | t₁ ≤ t₂        -- Integer/real comparisons
    | t₁ > t₂ | t₁ ≥ t₂
    | e ∈ S                    -- Set membership
    | d : e₁ → e₂              -- Dependency existence

Formulas (Quantifier-Free):

φ ::= a                        -- Atomic formula
    | ¬φ                       -- Negation
    | φ₁ ∧ φ₂                  -- Conjunction
    | φ₁ ∨ φ₂                  -- Disjunction
    | φ₁ ⇒ φ₂                  -- Implication
    | if φ₁ then φ₂ else φ₃   -- Conditional

Bounded Quantification (decidable extension):

φ ::= ∀ e ∈ E_finite. φ        -- Universal over finite set
    | ∃ e ∈ E_finite. φ        -- Existential over finite set

Normative SMT-LIB 2.6 Encoding

Definition 2.19 (SMT-LIB 2.6 Constraint Encoding): The following SMT-LIB 2.6 preamble defines the normative encoding for STRATUM constraints. Implementations MUST use this exact logic declaration and sort/function signatures for K0 conformance.

; SMT-LIB 2.6 Standard Preamble for STRATUM Constraints
(set-logic QF_AUFLIRA)  ; Combined logic: Arrays, Uninterpreted Functions, Linear Integer/Real Arithmetic

; Core domain sorts
(declare-sort Element 0)    ; Element identifiers
(declare-sort Layer 0)      ; Layer identifiers
(declare-sort Dependency 0) ; Dependency identifiers

; Element projection functions (uninterpreted)
(declare-fun elem-id (Element) Int)       ; Element → unique integer ID
(declare-fun elem-layer (Element) Layer)  ; Element → Layer membership
(declare-fun elem-type (Element) Int)     ; Element → type code

; Layer projection functions
(declare-fun layer-tier (Layer) Int)      ; Layer → tier code (0=motivation, 1=logical, 2=realization, 3=grounding)
(declare-fun layer-order (Layer) Int)     ; Layer → position within tier

; Dependency projection functions
(declare-fun dep-src (Dependency) Element)     ; Dependency → source element
(declare-fun dep-tgt (Dependency) Element)     ; Dependency → target element
(declare-fun dep-type (Dependency) Int)        ; Dependency → type code
(declare-fun dep-strength (Dependency) Int)    ; 0=soft, 1=hard

; Property access function (uninterpreted, domain-specific)
; Usage: (declare-fun prop-complexity (Element) Int)
; Each property gets its own typed accessor function

; Set cardinality (for finite element/dependency sets)
; Encoded as integer constants: |E| = elem-count, |D| = dep-count
(declare-const elem-count Int)
(declare-const dep-count Int)
(assert (>= elem-count 0))
(assert (>= dep-count 0))

; Tier ordering axioms (if needed for coherence constraints)
; (assert (forall ((l1 Layer) (l2 Layer))
;   (=> (< (layer-tier l1) (layer-tier l2))
;       (< (layer-position l1) (layer-position l2)))))
; Note: Quantifiers push logic to AUFLIRA (undecidable), avoid if possible

Logic Selection Rationale: QF_AUFLIRA combines four theories: Arrays (for element/dependency collections), Uninterpreted Functions (for property access), Linear Integer Arithmetic (for counts, tier codes), and Linear Real Arithmetic (for attenuation factors). This is the MINIMAL combined logic that supports all Kernel constraint patterns. Solvers: Z3 4.8+, CVC5 1.0+, MathSAT 5.6+ all support QF_AUFLIRA.

; Finite quantification over elements (expanded to conjunction)
; For specification with elements e1, e2, ..., en:
(assert (=> (is-feature e1)
            (or (and (tests-feature d1) (= (dep-src d1) t1) (= (dep-tgt d1) e1))
                (and (tests-feature d2) (= (dep-src d2) t2) (= (dep-tgt d2) e1))
                ; ... for all test elements t_i and dependencies d_j
            )))
; Repeat for e2, e3, ..., en

; Alternative encoding using counting (requires finite sets extension):
; (assert (forall ((f Element))
;   (=> (is-feature f)
;       (> (select feature-test-count f) 0))))
; where (declare-fun feature-test-count (Array Element Int))

Bounded Quantification Trade-off: Quantified formulas (∀, ∃) over finite element sets are DECIDABLE when expanded to finite conjunctions/disjunctions, but may cause exponential blowup. K0 implementations MAY choose to: (1) fully expand quantifiers at query-time (guarantees decidability, may be slow), OR (2) use heuristic quantifier instantiation (fast, may report 'unknown' for complex constraints). K1+ conformance REQUIRES full expansion with definite sat/unsat answers.

Resolution: When conflict(c₁, c₂), apply constraint with higher priority. If equal priority, flag for manual resolution.

4.2 Formal Policy Semantics#

DEF: §04-DEF-04-POLICY_EVALUATION_SEMANTICS#

evaluatePolicies : Spec × P(Violation) → P(PolicyAction)

Given specification S and violation set V, the policy evaluator returns the set of triggered actions:

evaluatePolicies(S, V) = ⋃_{p ∈ policies(S)} match(p, V)

where:
  match(p, V) = if triggers(p, V)
                then {⟨p.id, p.actions, violations_matched⟩}
                else ∅

  triggers(p, V) = ∃ v ∈ V. satisfies(v, p.appliesTo)

  satisfies(v, t) = (t.constraintCategories = ε ∨ v.constraint.cat ∈ t.constraintCategories)
                  ∧ (t.guarantees = ε ∨ violatesGuarantee(v) ∈ t.guarantees)
                  ∧ (t.integrityLevels = ε ∨ v.element.integrityLevel ∈ t.integrityLevels)
                  ∧ (t.severities = ε ∨ v.constraint.sev ∈ t.severities)

  violatesGuarantee : Violation → {'G1', 'G2', 'G3', 'G4', 'G5', 'G6', 'G7'}*
  violatesGuarantee(v) = { g | g ∈ guarantees(S) ∧ ¬g(S) ∧ v ∈ witnesses(g, S) }

DEF: §04-DEF-05-POLICY_CONFLICT_RESOLUTION#

When multiple policies trigger with conflicting blockingBehavior, resolve via priority:

conflictingPolicies(A) = { (a₁, a₂) ∈ A × A | conflicts(a₁.behavior, a₂.behavior) }

conflicts(b₁, b₂) = (b₁ = block_merge ∧ b₂ = auto_fix)
                  ∨ (b₁ = auto_fix ∧ b₂ = block_merge)
                  ∨ (b₁ = warn_only ∧ b₂ ≠ warn_only)

resolve(A) = if conflictingPolicies(A) = ∅
             then A
             else { a ∈ A | a.priority = max_{a' ∈ A} a'.priority }

finalBehavior(A) = let A' = resolve(A) in
                   if ∃ a ∈ A'. a.behavior = block_merge
                   then block_merge
                   else if ∃ a ∈ A'. a.behavior = auto_fix
                   then auto_fix
                   else warn_only

Theorem 2.2 (Policy Evaluation Determinism)

Proof Sketch: Each policy p is checked against each violation v (O(|P| × |V|)). The satisfies predicate evaluates in O(1) given finite sets. Conflict resolution selects highest-priority policy in O(|A|) where |A| ≤ |P|. Total: O(|P| × |V|) + O(|P|) = O(|P| × |V|). ∎

DEF: §04-DEF-06-POLICY_MERGE_SEMANTICS#

When composing specifications S₁ ⊕ S₂, policies merge with override semantics:

policies(S₁ ⊕ S₂) = override(policies(S₁), policies(S₂))

where:
  override(P₁, P₂) = { p ∈ P₁ | p.id ∉ ids(P₂) } ∪ P₂

  ids(P) = { p.id | p ∈ P }

Rationale: Higher-level compositions (e.g., project-level policies) override lower-level defaults (e.g., domain profile policies). This follows the 'configuration as code' principle where composition S₁ ⊕ S₂ means 'S₂ extends S₁ with overrides'.

Policy Evaluation: The operational implementation of evaluatePolicies(S, violations) follows Definitions 2.31-2.33 above. For validation integration, policies are evaluated after constraint checking per Operation 7.1 (validate). Policy conflict resolution uses priority ordering per §23 (same mechanism as Constraint priority).

Conformance: Policy system is K1 (Certified-Aware), not K0. K0 implementations may ignore policies. K1+ implementations MUST evaluate policies and respect blockingBehavior.

5 Well-Formedness Conditions#

5.1 Structural Well-Formedness#

A specification S is structurally well-formed iff all of the following hold:

WF-ID: Unique Identifiers

∀ e₁, e₂ ∈ E. e₁.id = e₂.id → e₁ = e₂
∀ l₁, l₂ ∈ L. l₁.id = l₂.id → l₁ = l₂
∀ d₁, d₂ ∈ D. d₁.id = d₂.id → d₁ = d₂
∀ c₁, c₂ ∈ C. c₁.id = c₂.id → c₁ = c₂
∀ b₁, b₂ ∈ B. b₁.id = b₂.id → b₁ = b₂

WF-LAYER: Layer Membership

∀ e ∈ E. ∃ l ∈ L. e.l = l.id

WF-TYPE: Type Vocabulary

∀ e ∈ E. let l = layer(e) in e.τ ∈ l.T

WF-DEP-ENDPOINTS: Dependency Endpoints

∀ d ∈ D. ∃ e₁, e₂ ∈ E. d.src.elem = e₁.id ∧ d.tgt.elem = e₂.id

WF-BINDING-SOURCE: Binding Sources

∀ b ∈ B. ∃ e ∈ E. b.abstract.elem = e.id

WF-LAYER-DEPS: Layer Dependencies

∀ l ∈ L. ∀ dep ∈ l.deps. ∃ l' ∈ L. l'.id = dep

WF-TIER-ORDER: Tier Ordering

∀ l ∈ L. ∀ dep ∈ l.deps. let l' = getLayer(dep) in pos(l') ≤ pos(l)

5.2 Tier Completeness#

WF-TIER-COMPLETE: All Tiers Present

∀ t ∈ TIER. ∃ l ∈ L. l.tier = t

This ensures the specification addresses all four fundamental questions:

  • motivation: WHY does this exist?

  • logical: WHAT is the structure?

  • realization: HOW does it work?

  • grounding: WHERE does it exist?

5.3 Acyclicity#

WF-ACYCLIC-LAYERS: No Layer Cycles

Let G_L = (L, {(l, l') | l' ∈ l.deps})
G_L is acyclic

WF-ACYCLIC-HARD: No Hard Dependency Cycles

Let G_D = (E, {(e₁, e₂) | ∃d ∈ D. d.src.elem = e₁.id ∧ d.tgt.elem = e₂.id ∧ d.σ = hard})
G_D is acyclic

Note: Soft dependencies MAY form cycles (for mutual references, etc.)

WF-SOFT-CYCLE-BOUNDED: Soft Cycle Boundaries

∀ cycle C in G_D^soft. ∃ d ∈ C. d.cascade_boundary = ⊤
where G_D^soft = (E, {(e₁, e₂) | ∃d ∈ D. d.src.elem = e₁.id ∧ d.tgt.elem = e₂.id ∧ d.σ = soft})

WF-CASCADE-TERMINATION: Cascade Depth Bounded

∀ r ∈ R. ∃ n ∈ ℕ. r.max_depth = n
∀ cascade path P in impact(S, e, r). |P| ≤ r.max_depth

6 Semantic Properties (The Seven Guarantees)#

6.1 Traceability#

DEF: §06-DEF-01-ROOT_ELEMENT#

root(e) ≡ layer(e).tier = motivation ∧ ¬∃d ∈ D. d.tgt.elem = e.id ∧ d.δ = traces_to

DEF: §06-DEF-02-TRACE_PATH#

tracePath(e) = shortest path from e to some e' where root(e') following traces_to dependencies from target to source (impl → requirement)

GUARANTEE G1 - TRACEABILITY

Every element traces back to a root element in the motivation tier (traces_to goes impl → requirement)

∀ e ∈ E. ∃ e' ∈ E. root(e') ∧ reachable(e, e', traces_to)

Formally, for specification S:
Traceable(S) ≡ ∀ e ∈ elements(S). tracePath(e) ≠ ∅

6.2 Completeness#

DEF: §06-DEF-03-CONSTRAINT_SATISFACTION#

S ⊨ c ≡ c.φ(elements(S), dependencies(S)) = ⊤

DEF: §06-DEF-04-ERROR_CONSTRAINTS#

ErrorConstraints(S) = {c ∈ constraints(S) | c.sev = error}

GUARANTEE G2 - COMPLETENESS

All error-level constraints are satisfied

∀ c ∈ ErrorConstraints(S). S ⊨ c

Formally:
Complete(S) ≡ ∀ c ∈ ErrorConstraints(S). c.φ(E, D) = ⊤

Common completeness constraints:

  • ∀ feature f. ∃ test t. tests(t, f) - Feature test coverage

  • ∀ api a. ∃ doc d. documents(d, a) - API documentation

  • ∀ aggregate ag. ∃ command c. commands(ag, c) - Aggregate has commands

6.3 Consistency#

DEF: §06-DEF-05-CONTRADICTION#

contradiction(e₁, e₂) ≡ ∃ property p.
e₁.π(p) is defined ∧ e₂.π(p) is defined ∧
e₁.π(p) ≠ e₂.π(p) ∧ shouldMatch(e₁, e₂, p)

DEF: §06-DEF-06-SHOULD_MATCH#

shouldMatch(e₁, e₂, p) ≡ ∃ c ∈ C. c.cat = consistency ∧ c specifies e₁.p must equal e₂.p

GUARANTEE G3 - CONSISTENCY

No two elements have contradictory properties

∀ e₁, e₂ ∈ E. ¬contradiction(e₁, e₂)

Formally:
Consistent(S) ≡ ∀ e₁, e₂ ∈ elements(S). ¬contradiction(e₁, e₂)

Common consistency constraints:

  • API return type = Handler return type

  • Event schema = Event handler expected schema

  • Database field type = Domain entity field type

6.4 Groundedness#

DEF: §06-DEF-07-LEAF_ELEMENT#

leaf(e) ≡ layer(e).tier = grounding

DEF: §06-DEF-08-BOUND_ELEMENT#

bound(e) ≡ ∃ b ∈ B. b.abstract.elem = e.id

GUARANTEE G4 - GROUNDEDNESS

Every leaf element has a binding to physical reality

∀ e ∈ E. leaf(e) → bound(e)

Formally:
Grounded(S) ≡ ∀ e ∈ elements(S). leaf(e) → bound(e)

Binding types per domain:

  • Software: Component → File:Line

  • Manufacturing: Part → Drawing + BOM

  • Healthcare: Protocol → EMR Configuration

  • Legal: Clause → Document Section

6.5 Determinism#

DEF: §06-DEF-09-CHANGE#

δ ::= ⟨element: ID, changeType: CHANGE, details: VALUE⟩

DEF: §06-DEF-10-IMPACT#

impact(S, δ) = ⋃ {cascade(S, elem(δ), δ.changeType, r) | r ∈ R, r.trigger matches δ}

GUARANTEE G5 - DETERMINISM

The impact of any change is predictable before making the change

∀ δ : CHANGE. impact(S, δ) is computable before applying δ

Formally:
Deterministic(S) ≡ impact : S × CHANGE → P(E × EFFECT) is total and computable in O(|E| + |D|) time

This enables:

  • Pre-change impact analysis

  • Automated change review

  • Risk assessment

  • Staged rollout decisions

6.6 Coherence#

DEF: §06-DEF-11-LAYER_RESPECTING#

layerRespecting(d) ≡ let l_s = layer(src(d)), l_t = layer(tgt(d)) in
pos(l_s) ≥ pos(l_t) ∨ d.δ = traces_to

GUARANTEE G6 - COHERENCE

Dependencies flow from concrete to abstract (except traces_to)

∀ d ∈ D. layerRespecting(d)

Formally:
Coherent(S) ≡ ∀ d ∈ dependencies(S). layerRespecting(d)

This ensures:

  • Abstraction boundaries are respected

  • Implementation details don't leak upward

  • Changes cascade predictably (down, not up)

Exception: traces_to dependencies go UP (from impl to requirement)

6.7 Explainability#

When validation fails, humans need actionable explanations. G7 requires that every violation report includes an irreducible unsat core—the minimal set of constraints causing the failure—and human-readable diagnostic text.

DEF: §06-DEF-12-EXPLANATION#

explanation ::= ⟨violatedGuarantee, unsatCore, blameChain, humanReadable, suggestedFix?⟩

where:

violatedGuarantee ∈ {'G1', 'G2', 'G3', 'G4', 'G5', 'G6', 'G7'}

Which guarantee failed

unsatCore ⊆ constraints(S)

Minimal unsatisfiable subset (see Theorem 10.12)

blameChain ∈ Operation*

Causal chain of changes leading to violation (uses vector clocks from §3.1 Element, §1)

humanReadable ∈ NAME

Natural language explanation targeting domain experts

suggestedFix ∈ Operation?

Optional: automated remediation per Policy (§2.8)

GUARANTEE G7 - EXPLAINABILITY

Every validation failure has an irreducible explanation with minimal unsat core

∀ violations v from validate(S). ∃ explanation x. explains(x, v) ∧ irreducible(x.unsatCore)

Formally:
Explainable(S) ≡ validate(S) produces explanations for all violations

Implementation: Use SMT solver unsat core extraction (Z3 unsat_core(), CVC5 getUnsatCore()). See Theorem 10.12 for irreducibility proof obligation.

Conformance: G7 is K1 (Certified-Aware), not K0. K0 implementations may return violations without explanations. K1+ implementations MUST provide irreducible unsat cores per Theorem 10.12.

Example: See §1.5 How to Read This Document Demo Scenario for complete G7 workflow showing blame chains and suggested fixes.

6.8 Valid Specification#

DEF: §06-DEF-13-VALID_SPECIFICATION#

Valid(S) ≡ WellFormed(S) ∧
Traceable(S) ∧ -- G1
Complete(S) ∧ -- G2
Consistent(S) ∧ -- G3
Grounded(S) ∧ -- G4
Deterministic(S) ∧ -- G5
Coherent(S) ∧ -- G6
Explainable(S) -- G7

A specification is valid iff it is well-formed and satisfies all seven guarantees. Note: G7 (Explainability) is K1 conformance; K0 implementations check G1-G6 only.

12 Formal Properties and Theorems#

12.1 Soundness#

Theorem 10.1 (Type Soundness - PROVEN):

If Γ ⊢ e : τ and e →* e' (e evaluates to e'), then Γ ⊢ e' : τ

Proof: By progress and preservation. The immutability of e.l (§3.1 Element) ensures that the covariant subtyping rule S-ELEMENT cannot be exploited to violate type safety. This follows the approach of Wright & Felleisen (1994).

Theorem 10.2 (Constraint Decidability - PROVEN):

For any constraint c with predicate φ in QF_LIA + QF_LRA + QF_UF:
  sat(φ) is decidable

Proof: QF_LIA, QF_LRA, and QF_UF are decidable fragments of first-order logic per SMT-LIB 2.6 standard. Decidability of the combination follows from the Nelson-Oppen procedure (1979), as these theories are stably infinite and have disjoint signatures (integer/real arithmetic operators vs uninterpreted functions).

Theorem 10.3 (Cascade Termination - PROVEN):

For any well-formed S and any cascade rule r:
  cascade(S, e, ch, r) terminates

Proof: By WF-ACYCLIC-HARD, hard dependency paths are finite. By WF-SOFT-CYCLE-BOUNDED, soft cycles have boundaries. By WF-CASCADE-TERMINATION, unbounded cascades have finite depth. The attenuation function eventually returns ⊥, ensuring propagation stops.

12.2 Convergence#

Theorem 10.4 (Strong Eventual Consistency):

For any replicas R₁, R₂ with seen(R₁) = seen(R₂):
  state(R₁) = state(R₂)

Proof [Enhanced v2.5]: The specification lattice (§9.3 Comparison Operations) forms a join-semilattice (L, ⊔, ⊑) with:

1. Join-semilattice properties:
- Associativity: (S₁ ⊔ S₂) ⊔ S₃ = S₁ ⊔ (S₂ ⊔ S₃)
- Elements: Add-wins set union is associative
- Dependencies: LWW with vector clocks is associative
- Constraints: Priority-based merge is associative (max is associative)

- Commutativity: S₁ ⊔ S₂ = S₂ ⊔ S₁
- Elements: Set union is commutative
- Dependencies: LWW breaks ties deterministically via vector clock total order
- Constraints: max(priority₁, priority₂) = max(priority₂, priority₁)

- Idempotence: S ⊔ S = S
- All component CRDTs (OR-Set for elements, LWW-Register for metadata) are idempotent

2. CRDT merge equivalence: merge(S₁, S₂) computes S₁ ⊔ S₂ by:

elements(S₁ ⊔ S₂) = elements(S₁) ∪ elements(S₂)  -- OR-Set merge
deps(S₁ ⊔ S₂) = lww(deps(S₁), deps(S₂))          -- LWW-Map merge
constraints(S₁ ⊔ S₂) = priority_max(...)          -- Priority merge



3. Convergence: For replicas R₁, R₂:
- Let ops₁ = operations seen by R₁
- Let ops₂ = operations seen by R₂
- If ops₁ = ops₂, then both replicas apply same set of operations
- Since ⊔ is associative and commutative, any ordering of ops yields same state
- Therefore state(R₁) = ⊔(ops₁) = ⊔(ops₂) = state(R₂)

4. Strong Eventual Consistency (SEC): By Shapiro et al. (2011) CMA theorem:
- Eventual Delivery: All operations eventually delivered to all replicas
- Convergence: Replicas with same operations have same state (proven above)
- Strong Convergence: No coordination needed (merge is deterministic)

Therefore, STRATUM specifications satisfy SEC. ∎

Theorem 10.5 (Merge Commutativity):

merge(merge(S₁, S₂), S₃) = merge(S₁, merge(S₂, S₃))

Proof: Follows from associativity of the join operation (Theorem 7.1).

14.3 Conflict Resolution Policies#

For concurrent operations on the same entity:

1. Add-wins (for elements, dependencies)

If op₁ = add(x) and op₂ = remove(x.id) and op₁ ∥ op₂: x is present in final state

2. Last-Writer-Wins (for properties)

If op₁ = update(e, p, v₁) and op₂ = update(e, p, v₂) and op₁ ∥ op₂: use v_i where op_i.clock is lexicographically greater

3. Priority-based (for constraints)

If conflict(c₁, c₂): if c₁.priority > c₂.priority then apply c₁; else if c₂.priority > c₁.priority then apply c₂; else flag for manual resolution

4. Union (for cascade rules)

All cascade rules from both replicas are kept. Duplicate rules (by id) are merged using LWW.

16.1 Migration Validity Preservation

Valid specifications remain valid after migration

If Valid(S) under Schema_old and migration is sound, then Valid(migrate(S, migration)) under Schema_new
Proof Sketch

Proof Sketch: By structural induction on the migration transform list.

Base case: Empty transform list. migrate(S, ⟨∅⟩) = S. Since Valid(S) under Schema_old and Schema_old = Schema_new (no changes), Valid(S) under Schema_new. ✓

Inductive case: Transform list t₁::ts. Assume Valid(S) and migration is sound.

1. Well-formedness preservation: Each transform type preserves WF-rules:
- set_default: Adds values to existing elements → preserves WF-ID, WF-LAYER, WF-ACYCLIC
- rename_field: Bijective renaming → preserves all structural properties
- compute_field: Pure function of existing data → preserves dependencies
- drop_field: Removal never violates WF-rules (may violate constraints)
- copy_field, split_field, merge_fields: Preserve element count and dependency graph

2. Guarantee preservation: Migration soundness requires:
- G1 (Traceability): Transform cannot remove traces_to edges → preserved
- G2 (Completeness): New error constraints satisfied by construction (migration transforms ensure this)
- G3 (Consistency): Transforms compute consistent values (no contradictions introduced)
- G4 (Groundedness): Bindings preserved or migrated with evidence
- G5 (Determinism): Cascade rules updated consistently
- G6 (Coherence): Layer positions unchanged → dependency directions preserved
- G7 (Explainability): Unsat cores re-computed for new schema

3. Constraint compatibility:
- Backward-compatible: Old constraints still valid (new fields optional or have defaults)
- Forward-compatible: New constraints don't reference removed fields
- Breaking changes: Migration MUST provide transforms that satisfy new required constraints

Migration soundness criterion: A migration is sound iff:

∀ transform ∈ migration.transforms.
  transform preserves WellFormed(S) ∧
  transform preserves {G1, G2, G3, G4, G5, G6} ∧
  (transform.type = add_field ⇒ ∃ default_value) ∧
  (transform.type = remove_field ⇒ field not referenced in constraints)



Termination: Migration applies finite transform list sequentially in O(|transforms| × |E|) time.

Therefore, Valid(S) ∧ Sound(migration) ⇒ Valid(migrate(S, migration)). ∎

21.2 Composition Properties#

DEF: §21-DEF-02-COMPATIBLE_SPECIFICATIONS#

Two specifications S₁ and S₂ are compatible (Compatible(S₁, S₂)) if and only if:

Compatible(S₁, S₂) ≡
  -- 1. No semantic conflicts in shared layers
  (∀l₁ ∈ S₁.layers, l₂ ∈ S₂.layers ·
    l₁.id = l₂.id →
      (l₁.tier = l₂.tier ∧ l₁.order = l₂.order)) ∧

  -- 2. No semantic conflicts in shared elements
  (∀e₁ ∈ S₁.elements, e₂ ∈ S₂.elements ·
    e₁.id = e₂.id →
      (e₁.layer = e₂.layer ∧ e₁.type = e₂.type)) ∧

  -- 3. No constraint conflicts (priority-based resolution)
  (∀c₁ ∈ S₁.constraints, c₂ ∈ S₂.constraints ·
    (c₁.scope ∩ c₂.scope ≠ ∅ ∧ c₁.kind = c₂.kind) →
      (c₁.priority ≠ c₂.priority ∨ c₁.predicate = c₂.predicate)) ∧

  -- 4. No circular cross-specification dependencies
  let D = S₁.dependencies ∪ S₂.dependencies in
  ¬hasCycle(D) ∧

  -- 5. Domain compatibility
  (S₁.domain ∩ S₂.domain ≠ ∅ ∨
   S₁.domain = "universal" ∨
   S₂.domain = "universal")

Rationale: Compatibility ensures that merging two specifications does not introduce semantic conflicts that would violate well-formedness. Condition (1) prevents layer tier/order mismatches. Condition (2) prevents element type mismatches. Condition (3) ensures constraint conflicts can be resolved by priority ordering (per §23). Condition (4) prevents dependency cycles. Condition (5) ensures specifications have overlapping domains or are universal.

23 Constraint Conflict Resolution#

23.1 Priority-Based Override Semantics#

When constraints conflict, resolution is determined by priority.

DEF: §23-DEF-01-CONSTRAINT_PRIORITY#

Priority sources (highest to lowest):

1. REGULATORY (priority 1000+)

Safety standard requirements (DO-178C, ISO 26262), Legal/compliance mandates, Regulatory body directives

2. SAFETY (priority 500-999)

ASIL-D/DAL-A requirements, Hazard mitigations, Security requirements

3. ARCHITECTURAL (priority 100-499)

System-level constraints, Interface contracts, Performance requirements

4. DESIGN (priority 10-99)

Component constraints, Module boundaries, Coding standards

5. PREFERENCE (priority 1-9)

Style guidelines, Naming conventions, Optional recommendations

DEF: §23-DEF-02-CONFLICT_DETECTION#

Two constraints c₁ and c₂ conflict iff:
∃ σ. sat(c₁, σ) ∧ sat(c₂, σ) ∧ ¬sat(c₁ ∧ c₂, σ)

Conflict types:

  • DIRECT: c₁ ∧ c₂ is unsatisfiable

  • INDIRECT: c₁ ∧ c₂ ∧ D is unsatisfiable (D = derived constraints)

  • RESOURCE: c₁ and c₂ compete for limited resource

  • TEMPORAL: c₁ and c₂ impose conflicting timing

23.2 Resolution Algorithm#

function resolveConflicts(C: Set<Constraint>) → ResolvedSet:
  conflicts := detectConflicts(C)
  resolved := {}
  overridden := {}

  for (c₁, c₂, type) in conflicts:
    if c₁.priority > c₂.priority:
      overridden.add(c₂)
      resolved.add({
        winner: c₁,
        loser: c₂,
        reason: 'priority',
        type: type
      })
    else if c₂.priority > c₁.priority:
      overridden.add(c₁)
      resolved.add({
        winner: c₂,
        loser: c₁,
        reason: 'priority',
        type: type
      })
    else:
      // Equal priority - flag for manual resolution
      resolved.add({
        winner: null,
        loser: null,
        reason: 'manual_required',
        type: type,
        constraints: [c₁, c₂]
      })

  return {
    active: C \ overridden,
    overridden: overridden,
    resolutions: resolved,
    manualRequired: resolved.filter(r => r.reason = 'manual_required')
  }

24 Garbage Collection Proofs#

24.1 GC Safety Requirements#

Garbage collection in CRDTs must preserve convergence properties.

DEF: §24-DEF-01-GC_SAFETY#

A garbage collection operation gc : State → State is SAFE iff:

GC-1 (Convergence Preservation)

∀ s₁, s₂. s₁ ⊔ s₂ = s₃ ⟹ gc(s₁) ⊔ gc(s₂) = gc(s₃)

GC-2 (Causal Stability)

gc removes tombstone t only if: ∀ replica r. r has observed t

GC-3 (No Information Loss)

∀ op. applicable(op, s) ⟹ applicable(op, gc(s))

DEF: §24-DEF-02-TOMBSTONE_STABILITY#

A tombstone t is STABLE at replica r iff:
∀ replica r'. r'.clock ≥ clock_at_creation(t)

Informally: All replicas have "caught up" past the tombstone creation.

Stability detection methods:

  • 1. VECTOR CLOCK COMPARISON: t stable when min(all_clocks) ≥ t.clock

  • 2. ACKNOWLEDGMENT: Each replica explicitly acks receiving t

  • 3. CHECKPOINT: Periodic global synchronization point

  • 4. TIME-BASED: t stable after duration D (requires clock sync)

24.2 GC Correctness Proofs#

Theorem 24.1 (Checkpoint GC Safety)

Given:
  - All replicas reach checkpoint C
  - Tombstone t was created before C
  - gc removes t after checkpoint
Then: gc satisfies GC-1, GC-2, GC-3

Proof:

  • GC-1: At checkpoint, all replicas have same state. gc applied uniformly to identical states produces identical results. ⊔ on identical states is idempotent, so gc(s) ⊔ gc(s) = gc(s). ✓

  • GC-2: Checkpoint C guarantees all replicas observed t. No replica can generate add operation for element with tombstone t (causally after). Therefore, t is stable. ✓

  • GC-3: Operations concurrent with t would have been merged before checkpoint. Post-checkpoint operations cannot conflict with t (causal order). ✓

27 Formal Attenuation Properties#

27.1 Attenuation Function Specification#

The attenuation function controls cascade propagation across layer boundaries. v2.4 adds formal properties required for safety analysis.

DEF: §27-DEF-01-ATTENUATION_FUNCTION_FORMAL#

attenuate : Impact × Layer × Layer → Impact

Signature:
attenuate(impact: Impact, source: Layer, target: Layer): Impact

Where Impact = { severity: ℕ, scope: Set<ElementID>, energy: ℕ }

DEF: §27-DEF-02-MONOTONICITY_REQUIRED#

∀ impact₁, impact₂, source, target:
impact₁.energy ≤ impact₂.energy
⇒ attenuate(impact₁, source, target).energy
≤ attenuate(impact₂, source, target).energy

(Larger inputs produce at-most-larger outputs; no amplification inversions)

DEF: §27-DEF-03-STRICT_REDUCTION_REQUIRED#

∀ impact, source, target where source ≠ target:
attenuate(impact, source, target).energy < impact.energy

(Crossing a layer boundary ALWAYS reduces energy; required for termination)

DEF: §27-DEF-04-BIBO_STABILITY_REQUIRED#

BIBO = Bounded Input, Bounded Output

∀ impact, source, target:
impact.energy ≤ MAX_ENERGY
⇒ attenuate(impact, source, target).energy ≤ MAX_ENERGY

(Bounded inputs produce bounded outputs; required for safety analysis)

DEF: §27-DEF-05-DEFAULT_TIER_ATTENUATION_FACTOR#

The DEFAULT attenuation function for K0 conformance is exponential decay:

γ(tier_diff) = 2^(-tier_diff) for tier_diff > 0
γ(0) = 1 for same-tier (no attenuation)

Example:
Tier 3 → Tier 2: γ = 0.5 (halved)
Tier 3 → Tier 1: γ = 0.25 (quartered)
Tier 3 → Tier 0: γ = 0.125 (eighth)

Alternative Attenuation Functions: Domain profiles MAY define custom attenuation functions iff they satisfy Definitions 28.2-28.4 (Monotonicity, Strict Reduction, BIBO Stability). K0 implementations MUST support the default exponential decay. K2+ implementations MAY support custom functions.

DEF: §27-DEF-06-ATTENUATION_FUNCTION_TYPE#

ATTENUATION_FUNCTION = { f : ℕ → [0,1] | satisfies(f, {Monotonic, StrictReduction, BIBOStable}) }

where:
Monotonic(f) ≡ ∀ n₁, n₂. n₁ ≤ n₂ ⇒ f(n₁) ≥ f(n₂)
StrictReduction(f) ≡ ∀ n > 0. f(n) < 1
BIBOStable(f) ≡ ∀ n. f(n) ∈ [0, 1]

Example Alternative Functions:
• Linear: γ(n) = max(0, 1 - 0.25×n) [satisfies all properties for n ≤ 4]
• Logarithmic: γ(n) = 1 / (1 + log₂(1+n)) [satisfies all properties]
• Step: γ(0)=1, γ(1)=0.5, γ(n≥2)=0.1 [satisfies all properties]

Composition of Attenuation Functions: When multiple cascade rules apply to the same dependency path, attenuation factors MULTIPLY: final_impact = initial_impact × γ₁ × γ₂ × ... × γₙ. Since each γᵢ ∈ (0,1], the product γ₁×γ₂×...×γₙ ∈ (0,1], preserving Monotonicity and Strict Reduction. This follows from the closure property of (0,1] under multiplication.

Theorem 28.1 (Cascade Bound)

Given:
  • Initial impact energy E₀
  • n tiers in specification
  • Minimum attenuation factor γ_min = 2^(-1) = 0.5
  • Energy threshold ε = 1 (minimum detectable impact)

Then:
  Total cascade energy ≤ E₀ × Σᵢ₌₀ⁿ⁻¹ γ_min^i = E₀ × (1 - γ_min^n)/(1 - γ_min)

For n = 4 tiers: Total ≤ E₀ × (1 - 0.5⁴)/(1 - 0.5) = E₀ × 1.875

Corollary (Path Termination): Any single cross-tier propagation path terminates in at most ⌈log₂(E₀/ε)⌉ steps.
Proof: After k steps, energy ≤ E₀ × (0.5)^k. Set E₀ × (0.5)^k ≤ ε and solve: k ≥ log₂(E₀/ε).

Note: Graph-wide cascade may have O(|E| + |D|) propagations, but each individual path is logarithmic.

For each UCA identified:

2. Map to STRATUM constraint:
{

3. Verify formal property:
□(speed > 0 ∧ obstacle → ◇≤100ms brakeCommand = ACTIVE)

G1: Traceability

Every element traces back to root in motivation tier. Formula: ∀ e ∈ E. ∃ e' ∈ E. root(e') ∧ reachable(e, e', traces_to)

G2: Completeness

All error-level constraints satisfied. Formula: ∀ c ∈ ErrorConstraints(S). S ⊨ c

G3: Consistency

No contradictory properties between elements. Formula: ∀ e₁, e₂ ∈ E. ¬contradiction(e₁, e₂)

G4: Groundedness

Every leaf element has binding to physical reality. Formula: ∀ e ∈ E. leaf(e) → bound(e)

G5: Determinism

Impact of changes is computable. Formula: ∀ δ. impact(S, δ) is decidable

G6: Coherence

Dependencies flow from concrete to abstract (except traces_to). Formula: ∀ d ∈ D. pos(layer(d.src)) ≥ pos(layer(d.tgt)) ∨ d.δ = traces_to

32.2 2. IMPACT ANALYSIS (<1 second)#

STRATUM's impact(S, change) operation traverses dependencies using the polarity table (v2.5 §3.3 Dependency). Dependency direction per v2.4.4 §3.3 Dependency: structural arrows point concrete → abstract, but CASCADE walks from changed element along dep arrows.

// Impact computation uses polarity-aware cascade
const impacted = impact(specification, change);

// Results (by dependency type per v2.5 policy table):
// realizes (backward, attenuate): 3 design elements in logical tier
// traces_to (backward, block): 7 code modules identified (no cascade)
// validates (both, block): 12 test cases flagged (bidirectional awareness)
// constrains (backward, attenuate): 2 safety constraints re-evaluated

Dependency Traversal:

  • realizes: Design-001 → REQ-042 (concrete depends on abstract). If REQ-042 changes, CASCADE finds deps where d.src=REQ-042 (none of type realizes), so no auto-cascade. But realizes has backward impact per v2.5: when requirement changes, designs depending on it need review (attenuated).

  • traces_to: Module-017 → REQ-042 (impl traces to req). This is upward structural dep (G6 exception). CASCADE behavior: block (no propagation, just flagging).

  • validates: Test-089 validates REQ-042 (bidirectional). Both elements flagged for review.

  • constrains: SafetyConstraint-005 constrains REQ-042. Constraint needs re-checking.

32.3 3. ATTENUATION CALCULATION#

Per §8.3 Cascade Computation CASCADE-ATT and v2.5 policy table, impact severity attenuates across tier boundaries:

// Attenuation function: γ = 2^(-tier_diff)
motivation tier:  100% impact (source tier)
logical tier:      50% impact (γ = 2^-1 = 0.5)
realization tier:  25% impact (γ = 2^-2 = 0.25)
grounding tier:    12.5% impact (γ = 2^-3 = 0.125)

attenuate(breaking) = degraded
attenuate(degraded) = cosmetic
attenuate(cosmetic) = none

32.4 4. VALIDATION WITH G7 EXPLAINABILITY#

STRATUM v2.5 adds G7 (Explainability) with irreducible unsat cores per [Z3-Cores]. Each violation includes a subset-minimal explanation.

// G2 (Completeness) VIOLATED
{
  violatedGuarantee: 'G2',

  blameChain: [

  suggestedFix: 'Reduce M-017 processing time to ≤95ms (allowing 5ms margin)'
}

// G4 (Groundedness) ✓ OK (all grounding-tier elements have bindings)

G7 Guarantee (v2.5 §6.8 Valid Specification): Every unsat core is irreducible (subset-minimal). This means: ∀c ∈ core: SAT(core \ {c}). Deleting any single constraint makes the core satisfiable, proving minimality. This is NOT the same as minimum-size (cardinality-minimal), which is NP-hard. Z3's deletion-based MUS extraction provides irreducibility in O(n × SMT) where n = |core|.
